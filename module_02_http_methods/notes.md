## Met1. POST + контрольное чтение

- POST /posts с телом {"title":"Мой пост","body":"Текст","userId":1} → 201 Created, id 101
- GET /posts/101 → 404 Not Found
- Вывод: песочница имитирует создание — отвечает 201, но данные не сохраняет. Запись проверяется только контрольным чтением.


## Met3. PUT vs PATCH

Тело запроса: {"name": "X"}

**PUT /users/2**
- Поля, которые послал: name
- Поля в ответе: id, name, username, email, address, phone, website, company
- Статус: 200 OK

**PATCH /users/2**
- Поля в ответе: те же поля целиком
- Статус: 200 OK

**Поля, которых не посылал, но они пришли:** id, username, email, address, phone, website, company

**Вывод (слияние или эхо):** эхо — песочница вернула все поля пользователя, не применив тело по-настоящему.

**Вопрос к себе.** Честный сервер: PUT стёр бы всё, кроме name; PATCH обновил бы только name. У jsonplaceholder — не так. Это ограничение песочницы, а не REST.


## Met4. DELETE

- DELETE /posts/3 → статус 200 OK
- Тело DELETE: полный объект поста (userId, id, title, body) — а не пустой {}
- Теория разрешает успеху DELETE: 200 (с телом) или 204 (без тела)
- Контрольный GET /posts/3 после удаления → 200 OK, тело содержит тот же пост

**Хватает ли одного статуса для веры:** нет
**Чего не хватает:** контрольного чтения

**Вывод:** песочница только имитирует удаление. Статус DELETE (200) ничего не доказывает. Только контрольный GET показал правду: ресурс никуда не делся — он по-прежнему доступен.

**Вопрос к себе.** Правду рассказывает контрольный GET, а не статус DELETE. У jsonplaceholder DELETE не удаляет — это ограничение симулятора, а не реального сервера. На боевом сервере DELETE /posts/3 действительно убрал бы ресурс, и GET вернул бы 404.


## Met5. Идемпотентность

### PUT /users/1 с телом {"name":"Dur"} — дважды

- Отправка 1: статус 200, тело: {id:1, name:"Dur", username, email, address, phone, website, company}
- Отправка 2: статус 200, тело: то же самое
- Ответы PUT совпали: да

### POST /posts с телом {"title":"T","body":"B","userId":1} — дважды

- Отправка 1: статус 201, id: 101
- Отправка 2: статус 201, id: 101 (у jsonplaceholder — всегда 101, потому что он не сохраняет)
- id совпали: да (но это свойство песочницы; на реальном сервере были бы 101 и 102)

**Вывод:** PUT — идемпотентен (повтор даёт тот же результат). POST — не идемпотентен (на реальном сервере каждый POST создаёт новый объект).

**Вопрос к себе.** Если два одинаковых POST дали разные id — сервер создал два объекта из одного тела. На странице оплаты двойное нажатие кнопки = два платежа.


## Met6. Таблица: безопасность и идемпотентность

| Метод | Безопасен? | Идемпотентен? | Обоснование |
| GET | да | да | Met3: два GET /users/1 → одинаковый ответ |
| POST | нет | нет | Met1, Met5: два POST → два разных объекта (на реальном сервере); на jsonplaceholder id всегда 101 |
| PUT | нет | да | Met5: два PUT /users/1 → одинаковый ответ |
| PATCH | нет | нет | выведено из теории 2.3, наблюдения нет |
| DELETE | нет | да | Met4: DELETE → 200, состояние «удалён» не меняется при повторе |


## Met7. Запахи REST

| Адрес | Где действие | Верная пара (метод + путь) |
| /api/getUsers | в пути (глагол getUsers) | GET /api/users |
| /api?action=deleteUser&id=5 | в query (action=deleteUser) | DELETE /api/users/5 |
| /users/5/remove | в пути (псевдоресурс remove) | DELETE /users/5 |
| /posts/delete-all | в пути (псевдоресурс delete-all) | DELETE /posts |

**Вопрос к себе.** Действие в query опаснее глагола в пути, потому что попадает в логи сервера и в историю 
браузера как безобидный GET — его может случайно выполнить любой переход по ссылке или предзагрузка страницы.


## Met8. curl: POST и GET

### Команда 1 — POST

```
curl -i -X POST https://jsonplaceholder.typicode.com/posts -H "Content-Type: application/json" -d "{\"title\": \"Мой пост\", \"body\": \"Текст\", \"userId\": 1}"
```

**Вывод:**

```
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Content-Length: 85
...
```

### Команда 2 — GET

```
curl -i https://jsonplaceholder.typicode.com/users/3
```

**Вывод:**

```
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Content-Length: 205
...
```

**Вопрос к себе.** Ключ `-i` показал заголовки ответа. Без него на экране осталось бы только тело JSON — и в багрепорте не было бы видно, какой статус и формат вернул сервер. Одного тела для воспроизведения бага мало: нужны метод, URL, тело запроса и заголовки ответа.
